## 0. 정의와 범위

**목적**
1. 서로 다른 모델·프롬프트·하네스에 **같은 성공 기준**을 적용한다.
2. 같은 평가 명세, 같은 증거, 같은 기준 시점 아래에서는 채점 환경이 바뀌어도 **판정이 재현 가능**해야 한다. 코드 채점기는 완전히 같은 판정을 요구한다. LLM judge는 판정 차이를 측정하고, 7.4절의 허용 범위 안에서 관리한다.
3. 점수 차이를 **비교 목적(5절)에 맞게** 해석한다.

**자산과 소모품의 구분**

| 구분 | 대상 | 관리 방식 |
|---|---|---|
| 자산(보존) | 평가 명세, 케이스, 루브릭, 채점기, fixtures, 기준 데이터 스냅샷, 실행 로그 | 버전 관리, 변경 이력 기록 |
| 소모품(교체) | 모델, 프롬프트, 하네스(Claude Code, Cursor, 자체 multi-agent), 도구 설정 | 어댑터 뒤에 두고, 실행할 때마다 manifest에 기록 |

**이식성의 세 종류**

| 종류 | 질문 | 검사(7.4절) |
|---|---|---|
| 실행 이식성 | 다른 하네스에서도 케이스를 실행하고 환경을 초기화할 수 있는가 | 인프라 원인 실행 불가 비율 |
| 의미 이식성 | 다른 하네스에서도 같은 성공 조건을 평가할 수 있는가 | 하네스 × 성공 기준 대응표 |
| 측정 일관성 | 같은 출력에 같은 판정이 나오는가 | 반복 채점, judge 계열 간 교차 채점 |

측정 일관성은 측정 타당성과 다르다. 두 judge가 같은 오류를 함께 놓치면 일관성은 높지만 타당성은 0이다. 타당성은 사람 기준과 비교해 따로 검사한다(7.4절).

하네스 사이의 점수 차이는 실행 이식성과 측정 일관성·타당성 검사를 통과한 경우에만 성능 차이로 해석한다. 그 성능 차이가 무엇을 뜻하는지는 비교 목적(5절)이 정한다.

## 1. 계층 구조

```
L1 Evaluation Specification   목적 · 모집단 · 성공 기준 · 기준 시점 · 판정 규칙 · 위험 등급
L2 Portable Assets            케이스 · 루브릭 · fixtures · 분할(split) · 스키마 · 버전
L3 Execution Adapters         Claude Code / Cursor / Raw API / 자체 multi-agent
L4 Outcome & Evidence         최종 상태 · 출력 · trajectory · 정책 이벤트 · manifest
L5 Grading & Validation       코드 채점기 → LLM judge → 사람
L6 Statistical Decision       판정 규칙 · 불확실성 · 이식성 검사 · 감사 기록
```

L1이 나머지 전부의 상위에 있다. 성공의 정의가 불명확하면 케이스와 채점기를 완벽하게 재사용해도 잘못된 것을 계속 측정하게 된다.

## 2. L1 Evaluation Specification

평가 대상마다 `spec.yaml` 하나를 둔다.

```yaml
spec_id: research-agent-v1
purpose: "공공 채용공고에서 국가공인 자격증을 정확히 추출"
population:                       # 이 평가가 대표하려는 실제 사용 분포
  segments: ["신규 사용자", "반복 사용자"]
  intents: {"조회": 0.6, "비교": 0.3, "예외 질문": 0.1}
success_criteria:
  - id: SC1
    description: "추출한 자격증이 공식 DB에 존재"
    kind: outcome                 # outcome: 최종 결과·상태로 판정
    grader_id: official_registry_check
    evidence_required: true
  - id: SC2
    description: "등록민간자격을 국가공인으로 분류하지 않음"
    kind: outcome
    grader_id: accreditation_classifier
    evidence_required: true
  - id: PC1
    description: "개인정보를 승인되지 않은 외부 대상으로 전송하지 않음"
    kind: policy                  # policy: trajectory와 감사 로그로 판정
    grader_id: egress_policy_check
    evidence_required: true
risk_tiers:
  critical: [SC2, PC1]
  normal: [SC1]
reference:                        # 채점 기준 데이터의 시점
  as_of: 2026-11-01
  snapshot_id: "registry-snapshot-2026-11-01"
decision:                         # 결과를 보기 전에 고정한다
  alpha_one_sided: 0.025
  power: 0.8
  margins:
    non_inferiority: 0.05         # 5%p 이내 하락은 "열등하지 않음"
    equivalence: 0.03             # ±3%p 안이면 "동등"
    cost_improvement: 0.20        # 성공 과제당 비용 20% 이상 감소
  owner: "제품 책임자 이름"          # 사업 판단이므로 결정권자를 명시
  fixed_at: 2026-11-01
```

**규칙**
- `decision`의 값은 결과를 보기 전에 정하고 날짜를 기록한다. 결과를 본 뒤 바꾸면 그 비교는 무효로 처리한다.
- 채점기는 실시간 DB가 아니라 `reference.snapshot_id`의 데이터로 채점한다. 공식 데이터가 바뀌면 같은 답변도 다르게 채점되기 때문이다. 스냅샷을 갱신하면 spec 버전을 올린다. 스냅샷이 다른 실행끼리는 비교하지 않는다.
- `population`은 blind 세트 표집과 세그먼트별 보고(5절)의 기준이다.

## 3. L2 Portable Assets

### 3.1 케이스 유형과 이동 규칙

| 유형 | 질문 | 기대 통과율 | `known_bad_ref` |
|---|---|---|---|
| `regression` | 이전에 하던 일을 계속 하는가 | 거의 100% | **필수** |
| `capability` | 아직 못 하는 일을 얼마나 하게 됐는가 | 낮게 시작 | 선택 |
| `safety` | 하면 안 되는 일을 하지 않는가 | 100% 목표 | 선택(사고 기반이면 필수) |

**관측값과 추정값을 구분한다.** 한 번의 실행에서 한 케이스의 "k회 모두 성공" 여부는 0 아니면 1이다. 이 값은 `observed_all_pass`로 기록한다. 케이스의 pass^k 추정값은 그 케이스의 누적 시행 n회 중 성공 c회로 C(c,k)/C(n,k)를 계산해 `est_pass_k`로 기록한다(τ-bench 추정식, n ≥ k). 두 값을 하나의 기준에 섞어 쓰지 않는다.

**capability → regression 이동**

| 단계 | 조건 | 의미 |
|---|---|---|
| 후보 | 깨끗한 환경에서 독립적으로 초기화한 최근 10회 시행이 모두 성공 | 신뢰성 입증이 아니라 이동 후보 조건이다. 시행당 성공률 0.8인 케이스도 10.7%, 0.9인 케이스도 34.9% 확률로 후보가 된다 |
| 이동 | 후보가 되면 regression으로 옮긴다 | 아래 누적 추적이 불안정 케이스를 걸러 낸다 |
| 재검토 | regression 케이스의 최근 30회 시행 누적 실패가 2건 이상 | 시행당 신뢰도 0.99면 3.6%, 0.95면 44.6%, 0.9면 81.6%, 0.8이면 약 99% 확률로 재검토 상태가 된다 |

- 재검토 상태가 되면 담당자가 둘 중 하나로 결정한다. (a) 실제 회귀다 → 시스템을 고친다. (b) 케이스 자체가 불안정하다 → capability로 강등한다.
- **자동 강등은 하지 않는다.** 자동으로 강등하면 실제 회귀가 강등에 묻혀 사라진다.
- 재실행으로 나온 성공이 실패 기록을 덮어쓰지 않는다. 모든 시행 결과는 누적 추적에 들어간다.
- "이 케이스의 시행당 실패율은 x% 이하"라고 주장하려면, 7.3절 안전 게이트 식으로 필요한 연속 성공 수를 채워야 한다(5% 이하라면 59회 연속 성공).

**양방향 쌍:** 어떤 행동이 일어나야 하는 케이스(예: 검색해야 하는 질문)에는 일어나지 말아야 하는 짝 케이스(검색 없이 답해야 하는 질문)를 `pair_id`로 묶는다. 한쪽만 평가하면 최적화도 한쪽으로 치우친다.

### 3.2 케이스 스키마

```yaml
id: SC2-0042
spec_id: research-agent-v1
type: regression                    # regression | capability | safety
criteria: [SC2]
severity: critical
pair_id: null
risk_family: classification-confusion   # 같은 결함을 공유하는 케이스 묶음(7.3절)
source:
  kind: incident                    # incident | trace | synthetic
  ref: "https://example.com/PR-1234"
input:
  query: "2026년 공공기관 AI 채용공고에서 국가공인 자격증만 추출"
expected:
  kind: state                       # state | rubric
  state: {classification: "등록민간자격"}
known_bad_ref: "runs/2026-10-20/SC2-0042.json"
split: regression                   # dev | regression | blind
added_at: 2026-11-01
```

모든 케이스 파일은 CI에서 `schemas/case.schema.yaml`(JSON Schema)로 검증한다. 검증에 실패한 케이스가 하나라도 있으면 eval을 실행하지 않는다. 스키마의 핵심 조건은 다음과 같다.

```yaml
$schema: "https://json-schema.org/draft/2020-12/schema"
type: object
required: [id, spec_id, type, criteria, severity, risk_family, source, input, expected, split, added_at]
properties:
  type: {enum: [regression, capability, safety]}
  split: {enum: [dev, regression, blind]}
  expected:
    oneOf:
      - {type: object, required: [kind, state], properties: {kind: {const: state}}}
      - {type: object, required: [kind, rubric_id], properties: {kind: {const: rubric}}}
allOf:
  - if: {properties: {type: {const: regression}}}
    then: {required: [known_bad_ref]}
```

### 3.3 분할(split)

| 분할 | 용도 | 접근 규칙 |
|---|---|---|
| `dev` | 일상 개발, capability 케이스, 프롬프트 튜닝 | 자유 |
| `regression` | 과거 실패의 재발 검사, CI 게이트 | 자유. 목적이 재발 방지이므로 튜닝 근거로 써도 된다 |
| `blind` | 독립 성능 검증 | 아래 규칙 |

**blind 세트 규칙**
- 접근 경로는 `blind_gate` 명령 하나다. 결과는 margin 기준 "통과 / 미달 / 판단 불가"만 반환한다. 세부 점수와 케이스별 결과는 반환하지 않는다. 세부 점수를 볼수록 blind 세트에 맞춘 조정이 쉬워지기 때문이다(Dwork 외, reusable holdout).
- 열람 예산은 분기당 2회(초기값)다. 열람할 때마다 `blind_access.log`에 날짜, 목적, 결과를 기록한다.
- 예산을 다 쓰거나, blind 결과를 보고 시스템을 고쳤다면 blind 세트 전체를 운영 트래픽에서 새로 표집한 세트로 교체한다. 교체 전 세트는 `dev`로 내린다.
- blind 세트는 `population` 분포에 맞춰 표집한다. regression 케이스(실패에서 만든 케이스)로는 전체 성공률을 추정하지 않는다.

### 3.4 루브릭

- 파일명에 버전을 붙인다: `rubrics/R-classify@v3.md`.
- 루브릭이 바뀌면 같은 비교에 쓰인 과거 출력도 새 버전으로 다시 채점하고, `rubric_changes.log`에 사유를 기록한다. 과거 실행의 환경이나 기준 스냅샷이 manifest상 다르면, 재채점 결과로 시스템 비교를 하지 않는다.

## 4. L3 Execution Adapters

**계약**

```
run(case, env_spec) -> Evidence {
  final_output, final_state,
  trajectory[{tool, args, result}],
  policy_events[{type, target, allowed}],   # 네트워크 송신, 파일 쓰기, 권한 변경
  tokens, latency_ms, cost, termination_reason, env_fingerprint
}
```

**규칙**
- 각 시행은 깨끗한 환경에서 시작한다. 컨테이너를 새로 만들고, 이전 시행의 파일·git 기록·캐시에 접근할 수 없게 한다.
- 예산 한도(시간, 호출 수, 비용)는 `env_spec`으로 고정한다.

**trajectory의 세 가지 용도**

| 용도 | 규칙 |
|---|---|
| 작업 성공 판정(`kind: outcome`) | trajectory를 쓰지 않는다. 최종 결과와 상태로만 판정한다. 에이전트가 예상하지 못한 정당한 경로를 찾을 수 있기 때문이다 |
| 정책 준수 판정(`kind: policy`) | trajectory와 `policy_events`로 판정한다. 금지 도구 호출, 허용 범위 밖 파일 쓰기, 승인되지 않은 외부 전송, 권한 상승이 하나라도 있으면 최종 결과가 맞아도 실패다 |
| 진단 | 비용·지연·불필요한 호출 분석(7.6절) |

**실행 실패 분류**

| 분류 | `termination_reason` 예 | 처리 |
|---|---|---|
| 인프라 | `container_start_failed`, `env_init_failed`, `provider_unavailable` | 최대 2회 재실행한다. 그래도 실패하면 "실행 불가"로 기록한다. 성능 집계에서는 빼되 뺀 건수를 함께 보고하고, 7.4절 실행 이식성 지표에 반영한다 |
| 시스템 | `budget_exceeded`, `tool_error`, `max_turns`, `loop_detected` | 과제 실패로 센다. 재실행하지 않는다. 어려운 케이스일수록 이런 실패가 많으므로, 빼면 성공률이 부풀려진다 |
| 정상 종료 | `completed` | 채점한다 |

## 5. L4 Outcome & Evidence: Run Manifest

실행마다 기록한다.

| 범주 | 필드 |
|---|---|
| 시스템 | 모델 id, 하네스 이름·버전, 프롬프트 해시, 도구 목록과 권한, temperature |
| 환경 | 실행 이미지 해시, 작업 저장소 커밋, 네트워크 접근 범위, 외부 데이터 접근 범위 |
| 예산 | 제한 시간, 최대 호출 수, 최대 비용 |
| 평가 | spec 버전, 케이스 세트 해시, 루브릭 버전, 채점기 버전, judge 모델과 최근 보정 결과, `reference.snapshot_id` |
| 실행 | 케이스별 시행 횟수, 케이스별 초기 상태 해시, 종료 상태 해시 |
| 비교 목적 | `component` / `controlled` / `system` |

**비교 규칙**
- **평가 필드는 모든 비교에서 같아야 한다.** spec 버전, 케이스 세트 해시, 루브릭·채점기·judge 버전, 기준 스냅샷 중 하나라도 다르면 비교를 거부한다.
- 시스템 필드의 허용 차이는 비교 목적에 따라 다르다.

| 비교 목적 | 시스템 필드 조건 | 결과의 의미 |
|---|---|---|
| `component` | 대상 요소 하나만 다르다 | 그 요소(예: 프롬프트 변경)의 효과 |
| `controlled` | 모델·하네스는 달라도, 도구 능력과 정보 접근(도구 목록, 네트워크, 데이터 접근, 예산)은 같게 맞춘다 | 같은 작업 조건에서의 모델·하네스 능력 차이 |
| `system` | 실제 제품 구성 그대로. 여러 요소가 함께 다르다 | 제품 전체의 차이. 특정 요소의 효과로 해석하지 않는다 |

- 결과는 L1 `population` 세그먼트별로도 나눠 보고한다. 세그먼트의 표본이 7.3절 기준보다 작으면 그 세그먼트의 결과는 "판단 불가"로 표시한다.

## 6. L5 Grading & Validation

### 6.1 채점기 선택 순서

1. 상태·코드 검증: DB 상태, 스키마, 테스트 실행, `policy_events` 규칙 검사
2. 보정된 LLM judge: 코드로 검증할 수 없는 기준에만 쓴다
3. 사람: judge 보정, 의미 이식성 검토, 표본 감사

코드 채점기는 **재현성**이 높을 뿐 **타당성**을 보장하지 않는다. 테스트를 통과했어도 명세가 요구한 것을 어겼을 수 있다.

### 6.2 채점기 검증

| 검증 | 내용 | 주기 |
|---|---|---|
| 자기 테스트 | `known_good`은 통과, `known_bad`는 실패해야 한다. 어기면 eval 실행을 중단한다 | 매 실행 |
| 우회 검사 | 채점 규칙은 통과하지만 명세를 어긴 출력(예: 테스트만 고친 diff)을 fixtures에 추가한다 | 새 실패 유형 발견 시 |
| 사람 대조 | 무작위 표본을 사람이 채점해 채점기 판정과 비교한다 | 월 1회 또는 채점기 변경 시 |
| 사람 라벨 품질 | critical 기준과 judge 보정용 라벨은 2명이 독립적으로 판정한다. 판정이 다르면 조정자가 최종 판정한다. 사람 간 kappa를 보고하고, 0.6(초기값) 미만이면 judge 보정보다 루브릭 수정을 먼저 한다 | 라벨 작성 시 |

자기 테스트는 필요조건이다. 알려지지 않은 정상 출력에 대한 오판은 사람 대조로만 잡힌다. 사람끼리도 합의하지 못하는 기준은 judge를 보정하는 기준이 될 수 없다.

### 6.3 LLM judge 규칙

- 한 judge는 한 기준만 판정한다.
- 출력은 `pass | fail | unknown` 세 가지다. 판정 전에 짧은 근거를 쓰게 한다.
- **양성 클래스는 "오류 있음(fail)"이다.**
  - TPR = 오류 탐지율 = judge가 fail로 판정한 실제 오류 / 전체 실제 오류
  - TNR = 정상 통과율 = judge가 pass로 판정한 실제 정상 / 전체 실제 정상
  - 정밀도 = 실제 오류 / judge가 fail로 판정한 전체. 실제 실패율이 낮으면 TPR·TNR이 높아도 정밀도는 낮다. 예를 들어 TPR·TNR이 0.9이고 실패율이 2%면 정밀도는 15.5%다.
- **`unknown` 처리**
  - `unknown`은 사람 검토 대기열로 보낸다.
  - 게이트 판정은 사람 검토가 끝날 때까지 보류한다.
  - 성능 보고에는 `unknown`을 모두 fail로 본 하한값과 모두 pass로 본 상한값을 함께 표시한다.
  - `unknown` 비율이 10%(초기값)를 넘으면 루브릭이 모호하다는 신호로 보고 루브릭을 고친다.
- judge 모델 버전을 고정한다. 기본값은 생성 모델과 다른 계열이다. 이것만으로 편향이 사라지지는 않으므로 사람 대조를 대신하지 않는다.
- **표본 기준은 전체 라벨 수가 아니라 실패 라벨 수로 정한다.** TPR 0.9 근처에서 95% 신뢰구간 반폭을 ±0.10으로 하려면 실패 라벨이 약 35개, ±0.05면 약 139개 필요하다. 실패율이 10%면 전체 라벨은 그 10배다.
- 재보정 조건: 생성 모델, judge 모델, 루브릭, 기준 스냅샷 중 하나라도 바뀌면 다시 보정한다.

## 7. L6 Statistical Decision & Audit

### 7.1 분석 단위

- 분석 단위는 **케이스**다. 같은 케이스를 여러 번 실행한 결과는 독립이 아니므로, 케이스 단위 clustered standard error를 쓰거나 케이스별로 요약한 뒤 분석한다.
- 안전 게이트에서는 `risk_family`도 분석 단위로 본다. 같은 결함을 공유하는 케이스끼리는 실패가 함께 일어날 수 있다.

### 7.2 판정 유형

| 판정 | 대상 | 방법 | 결과 표현 |
|---|---|---|---|
| 회귀 게이트 | `regression` | 아래 재현 실패 규칙 | 차단 / 통과 / flaky 의심 |
| 안전 게이트 | `safety` 케이스, `critical` 기준(`policy` 포함) | 실패 0건 요구. 인프라 실패는 통과로 세지 않는다. 재실행 후에도 실행 불가면 차단한다(fail-closed). 실패 확률 상한은 7.3절 조건으로 보고한다 | 차단 / 통과 |
| 비열등성 | 모델·프롬프트·하네스 교체 | 같은 케이스로 paired 비교. 개선 폭의 95% 신뢰구간(α=0.025 단측) 하한이 `-non_inferiority`보다 크면 열등하지 않음 | 열등하지 않음 / 판단 불가 / 열등 |
| 우월성 | 개선 주장 | paired 비교. 95% 신뢰구간 하한 > 0 | 개선 확인 / 확인 못 함 |
| 동등성 | "차이 없음" 주장 | TOST. 1−2α 신뢰구간(α=0.025면 95%)이 ±`equivalence` 안에 들어감 | 동등 / 판단 불가 |
| 비용 개선 | 비용·지연 개선 변경 | 품질이 비열등성을 통과하고, 성공 과제당 비용 또는 p95 지연이 `cost_improvement` 이상 감소 | 배포 가능 / 판단 불가 |

**"신뢰구간이 0을 포함하면 차이 없음"이라는 판정은 쓰지 않는다.** 그 경우의 결과는 "유의한 차이를 확인하지 못함"이다.

결과가 갈리는 케이스(한쪽만 성공한 케이스)가 25개 미만이면 정규 근사 대신 정확 McNemar 검정(갈리는 케이스에 대한 이항 검정)을 쓴다.

**회귀 게이트: 재현 실패 규칙**
1. 각 regression 케이스를 3회 실행한다. 모두 성공하면 그 케이스는 통과다.
2. 1회라도 실패하면 3회를 더 실행한다.
3. 6회 중 2회 이상 실패하면 **차단**한다. 실패가 재현됐다는 뜻이다.
4. 6회 중 1회만 실패하면 **flaky 의심**으로 기록하고 통과시킨다. 이 실패는 3.1절 누적 추적에 들어간다.

| 조건(케이스 100개) | v2 규칙(1회 실패 시 차단) | v2.1 규칙 |
|---|---|---|
| 회귀 없음, 시행당 신뢰도 0.99 | 95.1% 거짓 차단 | 11.1% |
| 회귀 없음, 시행당 신뢰도 0.995 | 77.8% | 2.9% |
| 회귀 없음, 시행당 신뢰도 0.999 | 25.9% | 0.1% |

케이스 하나가 실제로 회귀했을 때, 한 번의 게이트 실행에서 차단될 확률은 다음과 같다.
- 성공률이 0.5로 떨어진 경우: 82.8%
- 0.7로 떨어진 경우: 50.6%
- 0.8로 떨어진 경우: 29.1%

0.8로 떨어진 정도의 약한 회귀는 게이트 한 번으로는 잘 잡히지 않는다. 대신 3.1절 누적 추적(30회 중 2건 이상)에서 약 99% 확률로 재검토 상태가 된다.

**실행 주기**

| 대상 | 주기 |
|---|---|
| 회귀 게이트, 안전 게이트 | 프롬프트·모델·도구·검색 설정·채점기를 바꾸는 PR마다 |
| `dev` 세트 전체 | 매일 |
| `blind` 세트 | 3.3절 열람 예산 안에서 |
| 이식성 검사(7.4절) | 분기별, 또는 새 모델·하네스 도입 시 |

### 7.3 표본 수 계획 예시(가정 의존)

아래 수치는 다음 가정에서 나온 계획값이다. 실제 운영에서는 케이스 클러스터링, 층화, 반복 시행 구조를 반영해 검정력을 다시 계산한다.
- 정규 근사를 쓴다.
- 케이스끼리 독립이다. 같은 케이스의 반복 시행은 독립 케이스로 세지 않는다.
- α = 0.025(단측), 검정력 0.8, 실제 차이는 0이다.

**안전 게이트**

| 목표 실패율 상한(단측 95%) | 실패 0건일 때 필요한 독립 위험 사례 수 |
|---|---|
| 5% | 59 |
| 2% | 149 |
| 1% | 299 |

- 이 수는 **서로 독립인 위험 사례의 수**다. 같은 케이스를 299회 반복한 결과는 그 케이스의 시행당 신뢰도에 대한 증거일 뿐, 안전성 전반의 증거가 아니다.
- 같은 `risk_family`에 속한 케이스는 실패가 함께 일어날 수 있다. 그래서 family 수를 함께 보고한다. family 단위로 계산하면 상한이 크게 늘어난다. 예를 들어 family 10개에서 모두 실패 0건이면, family 단위의 실패율 상한은 25.9%다.

**비열등성(paired 비교)**: ψ는 결과가 갈리는 케이스의 비율이다.

| ψ | margin 5%p | margin 10%p |
|---|---|---|
| 10% | 314 케이스 | 79 케이스 |
| 20% | 628 | 157 |
| 30% | 942 | 236 |

**최소 검출 차이(검정력 80%)**: "검출 불가"는 최소 검출 차이가 ψ 이상인 경우다. paired 비교에서 두 시스템의 차이는 ψ보다 클 수 없으므로, 이 조건에서는 어떤 차이도 검출할 수 없다.

| 케이스 수 | ψ=10% | ψ=20% | ψ=30% |
|---|---|---|---|
| 50 | 검출 불가 | 17.7%p | 21.7%p |
| 100 | 8.9%p | 12.5%p | 15.3%p |
| 200 | 6.3%p | 8.9%p | 10.9%p |
| 400 | 4.4%p | 6.3%p | 7.7%p |

최소 검출 차이가 ψ에 가까운 칸은 정규 근사가 부정확하다. 그런 칸은 참고값으로만 쓴다.

### 7.4 이식성과 채점 검사

| 검사 | 방법 | 통과 기준(초기값) |
|---|---|---|
| 실행 이식성 | 각 어댑터로 전체 케이스 실행 | 인프라 원인 실행 불가 비율 ≤ 2%. 실행 불가 케이스가 특정 카테고리나 난이도에 몰려 있지 않은지 확인 |
| 의미 이식성 | 아래 대응표를 사람이 검토 | 대응할 수 없는 기준은 그 하네스에서 "측정 불가"로 표시하고, 그 기준의 점수는 비교에서 제외 |
| 측정 일관성 | 고정 출력 세트를 (a) 같은 judge로 반복 채점, (b) judge 계열 간 교차 채점 | 기준별 Cohen's kappa ≥ 0.6. fail 클래스 일치율을 함께 보고. 단순 일치율은 기준으로 쓰지 않음 |
| 측정 타당성 | 사람 조정 라벨(6.2절)과 비교 | 기준별 TPR(오류 탐지율) 95% 신뢰구간 하한 ≥ 0.8. critical 기준은 오류를 놓친 비율을 별도 보고 |

단순 일치율을 쓰지 않는 이유는 두 가지다.
- 출력의 95%가 통과인 기준에서, 무작위로 5%만 fail이라고 말하는 judge 두 개의 일치율은 90.5%다. 이때 kappa는 0이다.
- 두 judge가 같은 오류를 함께 통과시키면, 일치율은 100%인데 오류 탐지율은 0%다.

**의미 이식성 대응표 템플릿**

| 성공 기준 | Claude Code | Cursor | Raw API | 비고 |
|---|---|---|---|---|
| SC1 | `final_state` 등록정보 조회 | 같음 | 같음 | |

### 7.5 감사 기록

- `decisions.log`: 판정마다 manifest id, 판정 유형, 결과, 결정자
- `blind_access.log`: blind 세트 열람 이력과 교체 이력
- `rubric_changes.log`: 루브릭 변경과 사유
- `case_status.log`: flaky 의심, 재검토, 강등, 이동 이력과 담당자 결정
- 인시던트 사후 검토에서 "어느 계층이 이 문제를 잡았어야 했는가"를 기록하고, 해당 계층에 케이스나 fixture를 추가한다.

## 8. 축소판(소규모 팀용)

전체 v2.1이 과한 경우 아래만 먼저 운영한다.

1. `spec.yaml`: 성공 기준, 위험 등급, α, margin, 결정권자, 기준 스냅샷
2. `regression` 케이스 20~50개(`known_bad_ref` 포함), 코드 채점기, 자기 테스트, 스키마 검증
3. 깨끗한 환경 격리, 최소 manifest(모델, 하네스, 프롬프트 해시, 이미지 해시, 비교 목적), 실행 실패 분류
4. 판정은 회귀 게이트(재현 실패 규칙)와 안전 게이트(`policy` 기준 포함)만 쓴다

케이스 50개, ψ=20%이면 최소 검출 차이가 17.7%p이므로, 성능 비교 결과는 대부분 "판단 불가"가 나온다. 이것은 정상이다. 비열등성이나 우월성을 공식적으로 주장해야 하는 단계가 오면 그때 7.3절 표본 규모로 확대한다.
